# Рейтинг «Победа» — математическое ядро

Рейтинг «Победа» оценивает, выиграла или проиграла команда игрока в конкретной партии, и сравнивает этот факт с тем, чего от него ожидали: его сила относительно противников и сила его команды относительно команды соперников. Судейский балл в этом расчёте не участвует вообще — только исход игры и текущие рейтинги участников.

---

## 0. Идея: победа — командный факт, сравниваемый с ожиданием

У каждого игрока за игру есть ровно один факт — выиграла его команда или нет (`actual_win ∈ {0, 1}`, одинаковое значение у всех игроков одной команды). Этот факт сравнивается с ожиданием, которое складывается из трёх независимых источников:

1. **Асимметрия ролей** — чёрные (дон + мафия, 3 игрока) и красные (шериф + мирные, 7 игроков) не равны принципиально: это разные по самим правилам и механике игры роли, а не просто разное число игроков в команде. Поэтому «ничья по силе» для них — не 50/50, а эмпирическая величина, которую можно отследить через винрейт команды чёрных за последние N игр (например, за последние 1000 партий) — так асимметрия остаётся актуальной, а не зафиксирована раз и навсегда (`p_black_win`).
2. **Личная разница рейтингов** — насколько рейтинг игрока выше или ниже рейтинга конкретного соперника из другой команды.
3. **Разница силы команд** — насколько в среднем сильнее или слабее по рейтингу вся команда игрока по сравнению с командой соперника.

```
   actual_win ∈ {0, 1}                     ожидание победы
   (факт: выиграла ли моя команда)         (win_expectation)
            │                                      ▲
            │                      ┌────────────────┼────────────────┐
            │                      │                │                │
            │               асимметрия ролей    личная разница   разница силы
            │               (p_black_win)           рейтингов        команд
            │                      │                │                │
            │                      └────────────────┼────────────────┘
            │                                        │
            └──────────────────────┬─────────────────┘
                                    ▼
                      попарное сравнение (раздел 5):
                 actual_win минус то, чего ожидали от этой пары
```

Все три источника ожидания объединяются в одно число — `win_expectation` — а затем это число сравнивается с фактическим исходом для каждой пары «игрок — соперник из другой команды». Разница между фактом и ожиданием, просуммированная по всем соперникам, и есть сырой сигнал изменения рейтинга «Победа» за эту игру.

---

## 1. Входные данные

На входе — состав команд и исход игры:

```
чёрные = {дон, мафия}       (3 игрока)
красные = {шериф, мирные}   (7 игроков)

actual_win(p) =
    команда p победила   →  1
    команда p проиграла  →  0
```

---

## 2. Базовая вероятность победы чёрных

Идея: чёрные и красные не равны принципиально — по самим правилам и механике игры, а не просто по числу игроков в команде. Поэтому «справедливая» вероятность победы чёрных — не константа 50%, а эмпирическая величина, которую можно отследить через винрейт команды чёрных за последние N реальных игр (например, за последние 1000 партий) — так асимметрия остаётся актуальной, а не зафиксирована раз и навсегда. Эта вероятность дополнительно зависит от того, кто выбыл первым в партии — ранняя потеря шерифа или игра без первого убиенного меняют типичный расклад сил.

**Текущая реализация** (один из возможных вариантов):

```
p_black_win =
    array_avg(win_rate_array_no_fk),        если в партии никто не выбыл первой ночью
    array_avg(win_rate_array_fk_sheriff),   если первым выбыл шериф
    array_avg(win_rate_array_fk_other),     во всех остальных случаях

p_red_win = 1 − p_black_win
```

Каждый из трёх сценариев хранит собственное скользящее окно последних `N` валидных игр с тем же сценарием первого выбывания — новая игра дописывается в это окно, а значение `p_black_win` для следующей игры этого сценария берётся как среднее по накопленному окну. Размер окна свой для каждого сценария (раздел 8) — частый сценарий держит окно шире (стабильность на большом объёме данных), редкие — у́же (быстрее отражают реальную статистику, не застревают на старой выборке). Пока окно ещё не заполнилось реальными играми, величина стартует с нейтрального значения и постепенно вытесняется настоящей статистикой по мере накопления игр этого сценария.

`p_black_win` используется только как базовая составляющая ожидания (раздел 3) — личная и командная разница рейтингов добавляются поверх неё, а не вместо.

---

## 3. Ожидание победы: роль, личная сила и сила команды

Идея: ожидание того, выиграет ли игрок, должно учитывать не только его личный рейтинг относительно конкретного соперника, но и то, насколько сильна вся его команда относительно команды соперника — а также исходную асимметрию ролей из раздела 2. Используется логистическая функция, применённая не к базовым 50%, а к эмпирическому `p_black_win`/`p_red_win`.

**Текущая реализация** (один из возможных вариантов):

```
win_expectation(baseline, ri, rj, team_i, team_j) =
    sigmoid( logit(baseline)
             + win.lambda_pair · ln(10) · (ri − rj) / win.rating_scale
             + win.lambda_team · ln(10) · (team_i − team_j) / win.rating_scale )
```

Здесь `baseline` — это `p_black_win`, если игрок i чёрный, иначе `p_red_win` (раздел 2); `ri`/`rj` — текущие личные рейтинги «Победа» игрока и соперника; `team_i`/`team_j` — сила своей и чужой команды (раздел 4). `win.lambda_pair` и `win.lambda_team` — веса, с которыми личная и командная разница входят в ожидание: командная составляющая одинакова для всех сравнений игрока с любым соперником и отражает общий расклад партии, личная — это только собственная позиция игрока внутри своей команды. `win.rating_scale` — масштаб логистического ожидания: сколько пунктов разницы рейтинга нужно для заметного сдвига ожидания.

При `ri = rj` и `team_i = team_j` ожидание в точности равно `baseline` — то есть при полном личном и командном равенстве единственным источником ожидания остаётся эмпирическая асимметрия ролей.

## 4. Контекст стола: сила команд и волатильность

Это механика о ТЕКУЩИХ рейтингах игроков за столом, а не об исходе конкретной игры — она отвечает на вопрос «насколько резко должен двигаться рейтинг каждого конкретного игрока», а не «какая команда выиграла».

### 4.1 Сила команды и сила стола

Идея: нужна одна характеристика силы каждой команды — своей и чужой — для ожидания победы (раздел 3), а отдельно ещё общая характеристика силы всего стола, которая задаёт опорную точку для личной волатильности (4.2). Для обеих можно использовать любой подходящий агрегат.

**Текущая реализация** (один из возможных вариантов):

```
own_team_min      = min( win(p) по своей команде )
opponent_team_min = min( win(p) по чужой команде )
table_min         = min( win(p) по всем 10 игрокам )

own_team_strength      = own_team_min      + ( n_своей_команды / Σ ( win(p) − own_team_min      + win.table_strength_eps )⁻³ ) ^ (1/3) − win.table_strength_eps
opponent_team_strength = opponent_team_min + ( n_чужой_команды / Σ ( win(p) − opponent_team_min + win.table_strength_eps )⁻³ ) ^ (1/3) − win.table_strength_eps

table_win = table_min + ( n_игроков / Σ ( win(p) − table_min + win.table_strength_eps )⁻³ ) ^ (1/3) − win.table_strength_eps
```

Все три величины — одно и то же степенное среднее с показателем −3, применённое к разным группам игроков: `own_team_strength`/`opponent_team_strength` берут его в пределах одной команды (3 или 7 игроков), `table_win` — сразу по всем 10. Степенное среднее с отрицательным показателем сильно смещено к минимальным значениям, поэтому команда или стол характеризуются в первую очередь тем, насколько слаб среди них самый слабый участник, а не типичным/средним уровнем.

Формула применяется не напрямую к рейтингам, а к их ОТКЛОНЕНИЮ от минимума своей же группы, с постоянной `win.table_strength_eps`, возвращающей результат на исходную шкалу. Причина: степенное среднее с отрицательным показателем, применённое прямо к абсолютным значениям рейтинга, зависит от того, где на шкале рейтинга в данный момент находится вся группа — один и тот же по смыслу состав (тот же разброс сил между игроками) при сдвиге всех рейтингов на одну и ту же константу давал бы РАЗНУЮ силу команды или стола, иногда заметно отличающуюся. Привязка к минимуму группы убирает эту зависимость: результат не меняется от того, где именно на абсолютной шкале сидит вся группа, только от того, насколько игроки разошлись между собой.

`win.table_strength_eps` — не просто техническая защита от деления на ноль (у самого слабого игрока отклонение от самого себя иначе было бы ровно нулевым), а полноценная калибруемая величина: чем она меньше, тем жёстче формула реагирует на отстающего, чем больше — тем ближе её поведение к обычному среднему. На момент написания она равна 900 — подобрана так, чтобы как можно точнее воспроизводить сегодняшнее поведение формулы на реальных данных (разница от прежней, нескорректированной формулы — не больше 2–3 очков на любом из проверенных реальных столов). Это сознательная точка возможной будущей калибровки: если захочется, чтобы сила команды/стола ощутимее реагировала на отстающего игрока, `win.table_strength_eps` можно уменьшить — но на данный момент текущее значение эмпирически выглядит нормально и ожидаемо.

### 4.2 Волатильность относительно стола

Идея: рейтинг игрока должен двигаться мягче, когда он объективно сильнее стола — такому игроку мало что остаётся доказывать, и его не должно сильно шатать ни в одну из сторон. Важно: сама волатильность не знает исхода игры — она зависит только от разницы силы ДО игры, а не от того, кто в итоге победил. Один и тот же по величине множитель получает игрок независимо от того, выиграла его команда эту конкретную игру или проиграла; разным при этом будет не множитель, а то, что он домножает — разница между фактом и ожиданием из раздела 5. Если слабый относительно стола игрок неожиданно побеждает, эта разница большая (факт сильно разошёлся с ожиданием); если закономерно проигрывает — разница маленькая (поражение и так было ожидаемо), но в обоих случаях используется одна и та же, заранее известная по раскладу сил волатильность: она усиливает или ослабляет то, что получилось после сравнения с ожиданием, а не предсказывает сам исход.

**Текущая реализация** (один из возможных вариантов):

```
m_win(p) = min( tanh_m( table_win − win(p), win.volatility_player.min, win.volatility_player.max, win.volatility_player.scale ), 1 )

tanh_m(diff, min, max, scale) =
    diff ≥ 0  →  1 + (max − 1) × tanh(diff / scale)
    diff < 0  →  1 − (1 − min) × tanh(|diff| / scale)
```

Если рейтинг игрока НИЖЕ силы стола (`diff > 0`) — по формуле множитель рос бы выше 1, но внешний `min(..., 1)` срезает это сверху: слабый относительно стола игрок получает ровно базовый множитель 1, не усиленный. Если рейтинг ВЫШЕ силы стола (`diff < 0`) — множитель падает ниже 1, вплоть до `win.volatility_player.min`: рейтинг уже сильного игрока меняется более плавно. То есть на практике этот механизм только защищает сильных игроков от резких колебаний на слабых столах, а не усиливает волатильность слабых сверх базовой.

## 5. Где всё встречается: попарное сравнение с командой соперника

Это ядро всей механики: рейтинг «Победа» строится не на самом факте победы в отрыве от контекста, а на том, как этот факт соотносится с ожиданием — отдельно для каждого соперника из ДРУГОЙ команды. С игроками своей собственной команды сравнения не происходит: исход игры у игрока с ними всегда одинаковый, сравнение с союзником не несёт информации об исходе.

```
win_sum(p) = Σ_q∈чужая_команда  activity_factor(p, q) × min( m_win(p), m_win(q) ) × ( actual_win(p) − win_expectation(baseline, win(p), win(q), own_team_strength, opponent_team_strength) )

delta_win(p) = win.k × win_sum(p)
```

Здесь:

- **Сумма идёт только по игрокам ДРУГОЙ команды** — для чёрного игрока это 7 красных соперников, для красного — 3 чёрных. Своя команда в сумму не входит вообще.
- **`activity_factor(p, q)`** — понижающий множитель: если p или q выбыл первым в партии, слагаемое весит меньше — первым выбывший игрок даёт и получает меньше информации об игре.
- **`min(m_win(p), m_win(q))`** — берётся МЕНЬШИЙ из двух личных множителей волатильности пары, а не множитель самого `p`. Это сделано намеренно и критично для zero-sum (раздел 6).
- **`actual_win(p)`** — одно и то же значение (0 или 1) для всех слагаемых суммы одного игрока, поскольку исход игры у него один; меняется от слагаемого к слагаемому только `win_expectation`, поскольку он считается отдельно для каждой конкретной пары.
- **`win.k`** — единый финальный масштаб дельты за игру.

## 6. Почему сумма по столу равна нулю

Это не совпадение, а прямое следствие конструкции формулы: что получает один игрок за счёт сравнения с конкретным соперником из другой команды, ровно то же самое (с обратным знаком) теряет этот соперник в сравнении с ним.

Доказательство — для любой пары `(i, j)` из разных команд:

1. **`actual_win` антисимметричен для межкомандной пары**: ровно одна команда побеждает, поэтому если `actual_win(i) = 1`, то обязательно `actual_win(j) = 0` — и наоборот. Разница `actual_win(i) − actual_win(j)` всегда равна `±1`, симметрично по самому устройству исхода игры.
2. **`win_expectation` антисимметричен при обмене пары местами**: `win_expectation` для пары `(j, i)` в точности равен `1 − win_expectation` для пары `(i, j)`. Причина — `logit(p_red_win) = logit(1 − p_black_win) = −logit(p_black_win)` (стандартное свойство логит-функции), а оба слагаемых разницы рейтингов при перестановке `i` и `j` меняют знак на противоположный — в сумме весь аргумент сигмоиды меняет знак, что и даёт `sigmoid(−x) = 1 − sigmoid(x)`.
3. Отсюда `(actual_win(i) − win_expectation(i,j))` для пары `(i, j)` — это ровно минус то же выражение для пары `(j, i)`.
4. Все остальные множители — `activity_factor(i,j)` и `min(m_win(i), m_win(j))` — одинаковы в обе стороны: оба явно симметричны по построению, не зависят от того, с чьей точки зрения считать.

Итого: `raw(i,j) = −raw(j,i)` для каждой межкомандной пары, а значит и сумма по всем 10 игрокам `Σ delta_win(p) = 0` — всегда, точно, без приближений.

## 7. Скрытый тренд и видимый рейтинг

Идея: сырая дельта за игру — честный zero-sum сигнал, но сама по себе она может меняться слишком резко от игры к игре. Чтобы сгладить такие колебания, не теряя сам сигнал, вводится разделение на два параллельных числа: скрытый тренд, который копит реакцию на каждую игру без сглаживания, и видимый рейтинг, который меняется плавно, подтягиваясь к тренду, а не прыгая вслед за ним.

```
new_trend = trend + delta_win

gap = new_trend − win                                — разрыв между трендом и видимым рейтингом
dir_match = sign(delta_win) == sign(gap)              — совпадает ли направление этой игры с направлением разрыва

gap_component     = dir_match ? tanh(gap / win.smoothing.gap_scale) : 0
delta_r_component = tanh(delta_win / win.smoothing.delta_scale)

delta_visible = ( win.smoothing.trend_weight × gap_component + (1 − win.smoothing.trend_weight) × delta_r_component ) × win.smoothing.dv_max

new_win = win + delta_visible
```

- **`gap_component`** — «подтягивание к тренду»: чем больше накопленный разрыв, тем сильнее тянет видимый рейтинг в его сторону (с насыщением через `tanh`).
- **`dir_match`** — защита от «перекачки»: если эта конкретная игра тянет в сторону, противоположную уже накопленному разрыву, подтягивание по тренду в этот момент не применяется — работает только прямая реакция на игру.
- **`delta_r_component`** — прямая, несглаженная реакция на сырую дельту ЭТОЙ игры.
- Итоговое видимое изменение — взвешенная смесь этих двух компонент (`win.smoothing.trend_weight`), с общим потолком `win.smoothing.dv_max` очков за игру.

### 7.1 Ограничение тренда (опционально)

Поскольку тренд копится без ограничения на шаг, со временем он может уйти очень далеко от видимого рейтинга (особенно за длинную серию игр в одну сторону). Есть опциональный параметр `win.trend_bound` (число или отключение), который держит тренд в пределах `visible ± trend_bound`.

Важное свойство реализации: ограничение влияет только на то, что реально сохраняется в тренд — весь расчёт ВИДИМОГО рейтинга из раздела 7 выше (gap, dir_match, gap_component, delta_r_component) считается по-прежнему от неограниченной сырой дельты, как если бы ограничения не было вовсе. Разница только в том, какое число в итоге запоминается как `trend` для следующей игры.

Чтобы ограничение не портило zero-sum из раздела 6, оно устроено в два прохода:

1. Для каждого игрока находится коэффициент `β`, на сколько процентов пришлось бы урезать сырую дельту, чтобы новый тренд не вышел за `visible ± trend_bound`.
2. Каждый парный `raw(p, q)` из раздела 5 домножается не на `β(p)` отдельно, а на `min(β(p), β(q))` — тот же приём, что и с `min(m_win(p), m_win(q))`: общий множитель на пару, а не личный множитель каждого, иначе сумма по столу перестала бы сходиться в ноль.

## 9. Сводная цепочка (для быстрой справки)

```
actual_win (факт: победила ли команда игрока)
        │
        │              p_black_win / p_red_win (раздел 2)
        │                              │
        │                              ▼
        │                 win_expectation(baseline, личный рейтинг, рейтинг соперника,
        │                              сила своей команды, сила команды соперника)
        │                              ▲
        │               ┌───────────────┴───────────────┐
        │        личная разница                   разница силы
        │        рейтингов                          команд
        │                              │
        └──────────────┬───────────────┘
                        ▼
     для каждого соперника q из ДРУГОЙ команды:
     actual_win vs win_expectation(q)
     raw(p,q) = activity_factor(p,q) × min(m_win(p), m_win(q)) × (actual_win(p) − win_expectation(q))
                        ▼
     win_sum(p) = Σ raw(p,q)  →  delta_win(p) = win.k × win_sum(p)
                        ▼
     new_trend = trend + delta_win   (копится без ограничения, либо мягко — trend_bound)
     gap, dir_match, gap_component, delta_r_component
                        ▼
     new_win = win + delta_visible
```

## 10. Оговорки

Ниже — несколько сознательных особенностей текущей реализации, которые стоит иметь в виду при интерпретации рейтинга.

- **Рейтинг не учитывает судейские оценки вовсе.** Единственное, что для него имеет значение, — выиграла или проиграла команда игрока (раздел 1), его текущий рейтинг и рейтинги соперников. Это сознательная особенность, а не недосмотр: рейтинг «Победа» измеряет именно и только результат команды относительно ожидания, не пытаясь судить о качестве игры внутри партии.
- **Победа — чисто бинарный факт, без понятия «уверенности» или перевеса.** `actual_win ∈ {0, 1}` (раздел 1) не различает убедительную победу и победу на тонкой грани — учитывается только сам факт «выиграл/проиграл» команды, а не то, насколько решительным было превосходство. Это прямое следствие природы самой игры: у партии в мафию нет непрерывной шкалы «насколько сильно одна команда переиграла другую» — есть только бинарный исход.
- **В волатильности пары побеждает более стабильный участник, а не более информированный.** `min(m_win(p), m_win(q))` (раздел 5) берёт МЕНЬШУЮ из двух личных волатильностей пары. Множитель игрока, который слабее стола, никогда не поднимается выше базового значения 1 — внешний `min(..., 1)` в разделе 4.2 срезает рост; множитель игрока, который сильнее стола, наоборот, опускается ниже 1 по мере того, как он превосходит стол. Из-за этого минимум из пары почти всегда оказывается множителем более сильного участника сравнения. Это намеренный приоритет: механизм в первую очередь защищает сильных игроков от резких колебаний на слабых столах, а не ускоряет обучение более слабых относительно стола игроков — если бы приоритет был обратным, в разделе 5 использовался бы `max`, а не `min`.
- **Сумма по чужой команде не нормируется на её размер.** Чёрный игрок складывает слагаемые по 7 красным соперникам, красный — по 3 чёрным (раздел 5), и `delta_win = win.k × win_sum` использует один и тот же `k` для обеих сторон, без деления на число слагаемых. Поскольку слагаемые одной игры сильно коррелированы по знаку (а не независимый шум — все они считаются от одного и того же `actual_win` этого игрока), сумма у чёрных типично по модулю заметно больше, чем у красных: при прочих равных рейтинг дона/мафии может двигаться сильнее, чем рейтинг шерифа/мирного, просто из-за разницы в размере команд. Это можно объяснить тем, что ответственность за победу или поражение распределяется между разным числом игроков в зависимости от команды, и для чёрных условия чуть строже: каждый из них сильнее отвечает за исход своей команды, чем отдельный игрок у красных. Это оставлено как есть осознанно — не корректируется отдельным множителем или делителем на размер команды соперника.
- **Отдельные базовые вероятности по сценарию первого выбывания — осознанный выбор.** Три сценария раздела 2 (никто не выбыл первой ночью, первым выбыл шериф, первым выбыл кто-то другой) учитываются не из технической прихоти: оба особых случая — отсутствие ранней потери и ранняя потеря именно шерифа — происходят практически в самом начале партии и существенно меняют сложность победы для той или иной команды. Именно поэтому `p_black_win` разделён по сценарию, а не считается одной общей вероятностью на все игры.
- **Двойной учёт рейтинга игроков — в личном сравнении и отдельно в силе команды/стола — осознанное решение.** Один и тот же рейтинг каждого из 10 игроков участвует и в личной разнице (раздел 3), и в расчёте силы команды и стола (раздел 4), то есть формально считается дважды. Это сделано намеренно: в мафии общая сила стола и команды — не второстепенный фактор, а то, что во многом определяет саму возможность команды победить, поэтому её стоит учитывать отдельно от личного сравнения, даже если оба расчёта опираются на одни и те же исходные рейтинги.
- **Выбор степенного среднего с показателем −3 — не произвольный.** И сила стола, и сила команды (раздел 4.1) считаются степенным средним, сильно смещённым к минимальному значению, а не обычным средним. Причина — в самой механике игры: самый слабый игрок за столом или в команде чаще всего «тащит» её на дно, и именно на нём пытаются сыграть игроки противоположной команды, чтобы добиться победы. Это, конечно, абстрактное обобщение, а не строгий закон, но в целом это реальная тенденция игры, которую степенное среднее с отрицательным показателем отражает лучше, чем обычное арифметическое.
- **Видимый рейтинг — не zero-sum, в отличие от тренда.** Доказательство раздела 6 строго для сырой дельты `delta_win`: её сумма по столу равна нулю точно, без исключений — и ровно то же самое верно для прироста скрытого тренда за игру (`new_trend = trend + delta_win`), поскольку тренд копит именно эту сырую дельту напрямую. А вот то, что видит пользователь (`win_*`), получается из неё через сглаживание (раздел 7) — `tanh`-сжатие и общий потолок `smoothing.dv_max`, нелинейные преобразования, после которых сумма изменений по столу уже не обязана быть нулевой. Это сознательное решение: цель сглаживания — ограничить, насколько сильно видимый рейтинг может измениться за одну игру, а не сохранить точный zero-sum на каждом шаге. От неконтролируемой инфляции или дефляции видимый рейтинг защищает не точный баланс сумм, а два других механизма: подтягивание к тренду (`gap_component`, раздел 7) и ограничение на то, насколько далеко тренду разрешено уйти от видимого рейтинга (`trend_bound`, раздел 7.1) — вместе они не дают видимому рейтингу надолго разойтись с честно нулевым по сумме скрытым трендом.
- **Вся механика — отражение эмпирического опыта, а не математической необходимости.** Выбор конкретных формул, констант и приоритетов в этом документе не единственно возможный и не продиктован математикой как таковой — это результат наблюдения за реальными играми, их развитием во времени, и суждений о том, какие вещи оказались существеннее других. Это не значит, что выбор произволен — за каждым решением стоит конкретная причина, изложенная в соответствующем разделе, — но ни одно из них не стоит считать раз и навсегда зафиксированным. Это предмет постоянной дискуссии и точка роста, которую стоит пересматривать по мере накопления новых статистических и эмпирических наблюдений.
